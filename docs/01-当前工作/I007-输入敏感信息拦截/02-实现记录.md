## 行为约定（用户可见）

- Enter 命中阻断类规则：拦下发送并提示命中的规则名。
- Enter 命中脱敏类规则：`maskOnSubmit` 为真时就地打码 + 提示；为假时只提示、不改写。
- Enter 命中词条映射：拦下本次发送、就地改写草稿、**不发任何提示**；用户需**再按一次 Enter**。该静默行为已写入双语 README 与 CHANGELOG。
- 粘贴命中阻断类规则：`preventDefault` 取消粘贴 + 提示。
- 粘贴命中脱敏类或映射：先放行落地，再在 `input.state` 订阅回调里按整篇草稿重算改写（避免只处理片段）。
- 草稿含结构化引用或图片时整体退让，不调用 `setDraft`（硬性互斥条件）。
- 卸载插件即完全失效，不改动宿主与 Codex UI 的任何数据或配置。

## 后续修复：Enter 拦截失效与号码覆盖缺口

| --- | --- | --- |
| `13800138000` | ✅ `138****8000` | ✅ 同 |
| `138 0013 8000` | ❌ 放行 | ✅ `138****8000` |
| `138-0013-8000` | ❌ 放行 | ✅ `138****8000` |
| `008613800138000` | ❌ 放行 | ✅ `0086138****8000` |
| `010-12345678` | ❌ 放行（规则不存在） | ✅ `010****5678` |
| `021 1234 5678` | ❌ 放行 | ✅ `021****5678` |

| `95588` / `10086` | ❌ 放行 | ✅ `9****` / `1****` |
| `01012345678`（无分隔符） | 放行 | 放行（设计内） |
| `95200`、`400 123456` | 放行 | 放行（白名单/位数把关） |

因此归因为两件事，均属本插件自身缺陷：

### 一、接线缺陷：Enter 可能整体不拦截（严重）

原实现把 `keydown` 绑在输入框元素上。**DOM 规范里事件到达 target 时，同一节点上的监听器按注册顺序执行，capture 标志不改变 target 阶段的顺序。**
宿主 Lexical root 在编辑器挂载时先注册提交处理器，本插件 dock 在 effect 中后注册 → 宿主先执行并 `preventDefault`（提交时必然阻止换行），
本插件随后读到 `event.defaultPrevented === true` 直接放行——命中凭证或个人信息也不会拦截。

`bindHistoryKeys` 用同一套守卫却看不出问题，是因为它只处理 ↑/↓，这两个键宿主不抢，`defaultPrevented` 分支从未被真正检验。

修法：监听从 editor 改到 `document` **捕获阶段**（`ownerDocument.addEventListener('keydown', handler, true)`），
作用范围仍由 `editor.contains(event.target)` 限定；粘贴路径一并提升。这样先于宿主 target 监听器执行，能真正拦下本次发送。

### 二、规则缺口：号码覆盖不足（明显）

`cn-mobile` 原正则只认「连续 11 位」，且规则表里没有固话与服务号。修法：

- `cn-mobile` 容忍 `+86`/`0086` 前缀与空格、短横分组，掩码统一归一为前三后四；
- 新增 `cn-landline`：要求至少一处分隔符（连续数字更可能是账号），并校验区号与 7–8 位号码；
- 新增 `cn-service-number`：`400`/`800` 按「三位 + 七位」结构，五位短号只认公开客服号白名单，把五位纯数字的误报压到零。

### 三、诊断盲区

`apply` 未执行、`ctx.sessions.binding()` 返回 undefined、`findComposer()` 找不到输入框，三处原先都静默无日志，装完插件无法判断死活。
现分别输出一条控制台信息（后两者用 ref 去重，只提示一次），已写入双语 README 的「诊断」小节。

## 补充修复（0.1.2）

时间：2026-09-14 13:29（Asia/Shanghai）。起因：用户重启后控制台只出现「客户端半边已加载」这一条，据此逐层核对注册链路，查出三个问题。**前两个都不是「猜」出来的，是照着根包（工作正常的 `@michengai/dsh-codex-ui`）对照出来的。**

### 一、运行时词库未注册（确定的缺陷）

宿主词库里因此没有 `michengai.inputGuard`：带 `locale` 的插槽拿不到词典，`t('guard.blocked')` 会退化成 key 本身。

> 这一条**不是**「不脱敏」的原因——拦截逻辑不依赖文案——但会让提示显示成 `guard.blocked`，属必修项。

### 二、dock 层测试从未执行（假绿，代价最大的一个）

包内 `vitest.config.ts` 的 `include` 是 `tests/**/*.spec.ts`，而 dock 测试文件叫 `guard-dock.spec.tsx` —— **扩展名不匹配，vitest 从未收集它**。
dock 层 15 条用例（提交路径 B、粘贴路径 C、诊断）此前一直是摆设，`pnpm test` 却显示全绿。

改名为 `guard-dock.spec.ts`（按仓库惯例，spec 一律 `.ts`，React 用例用 `createElement` 而不写 JSX）后，**立刻暴露两个真实缺陷**：

1. `connect()` 用 `undefined === undefined` 判定「状态未变」：首次就找不到输入框时直接 return，**既不告警也不重试**，诊断日志形同虚设。现用专门的哨兵区分「尚未查找」与「查找过但没找到」。

### 四、状态读取崩溃让 Enter 完全穿透（0.1.3，**「不脱敏」的真正根因**）

用户重启后控制台证明三层注册全部通过（已加载 → 已注册插槽 → 已绑定输入框），但紧接着出现：

```
[client-store] subscriber failed: TypeError: Cannot read properties of undefined (reading 'length')
    at busy (…:104265:87)  … at SessionInputShell.publish
Uncaught TypeError: Cannot read properties of undefined (reading 'length')
    at Object.busy (…:104265:87)  at HTMLDocument.keydown (…:104185:22)
```

`busy()` 里的 `state.occurrences.length`：宿主在相位切换期间会发出**缺字段的中间态**（`occurrences` 为 undefined），
直接读 `.length` 抛 TypeError；异常从我们的 keydown 处理器逃逸到 window（Uncaught），**本次 Enter 既没被拦下也没改写**，宿主照常发送。

修法两层：

1. **只声明插件真正用到的字段并全部按可选处理**：`occurrences?.length ?? 0`、`imageIds?.length ?? 0`、`draft ?? ''`、`phase` 缺失按 `plain` 处理；
2. **拦截路径异常隔离**：keydown 与 paste 整体包 `try/catch`，任何内部异常都不再逃逸（改为放行本次 + `console.error` 留痕），粘贴后的整篇重算同样隔离。

> 教训：**读第三方运行时状态永远不能假设字段齐全**。事件处理器里的一次读取抛错，不是「少做一件事」，而是**整条拦截链路失效**。

回归覆盖：dock 层新增「宿主状态缺少 `occurrences`/`imageIds` 时仍能正常拦截」；guard-keys 层新增「读取状态抛错时隔离异常并放行本次按键」。

部署（0.1.3）：tgz `input-guard-20260914-1332`，备份 `backup-20260914-1332`，哈希与工作区构建一致，
bundle 内已确认含 `occurrences?.length` 与 `拦截过程中出错，本次放行：`。用例 116 → **118**。

### 五、Enter 不触发的定位（0.1.4）

用户反馈：**复制粘贴会正常触发，直接输入发送不触发**。这个差异本身就是最强线索——paste 路径不经过 `busy()` 与 IME 守卫，
说明插件加载、插槽注册、输入框绑定、识别引擎、`setDraft` 全部正常，问题只落在 Enter 的守卫链上。

守卫链原本是「静默放行」，无法再靠推断，于是给每条放行分支加**一次性诊断**（每条原因只提示一次，正常聊天不会刷屏）：

| 日志 | 含义 |
| --- | --- |
| `Enter 未拦截：更早的处理器已处理（defaultPrevented）` | 宿主比插件更早处理了这次按键 |
| `Enter 未拦截：输入法组合中（composing 标志）` | composition 状态未被清除 |
| `Enter 未拦截：输入法组合中（isComposing / keyCode 229）` + 明细 | IME 组合中按下的 Enter |
| `Enter 未拦截：相位繁忙或触发菜单打开` + `phase= occurrences= images= menuOpen=` | 互斥条件命中，且指明是哪一条 |
| `Enter 未拦截：未命中任何规则` + `草稿长度=` | 引擎判定放行（只报长度，不把草稿内容写进控制台） |

同时修掉一个会造成**永久放行**的隐患：`composing` 标志原先只在输入框元素上监听 `compositionend`，
组合一旦在别的节点结束就会卡在 `true`，此后**所有 Enter 都被放行**。
现改为在 `ownerDocument` 捕获阶段监听，且 `compositionend` **无条件**清除标志。

### 六、提示改为自绘浮层并 3 秒隐藏（0.1.5）

脱敏确认正常工作后，用户提出：脱敏提示在发送后 3 秒隐藏。

先查证据再改：宿主 `input.notify` 只往 InputNotice 列表写一条，
`@deepseek-ai/dsh-client-ui-conversation@0.1.5-rc.1` 的实现里**与该列表相关的 `setTimeout` 为 0 处**，
也没有 `dismiss`/`clear` 一类接口——**提示一旦推送就常驻**，插件无法让宿主提示定时消失。

因此改为插件自绘浮层（新增 `src/client/guard-notice.ts`）：

- 显示 3 秒后自动隐藏；重复提示复用同一元素并重新计时；
- 宿主提交成功（草稿清空）后 `hold()` 续期 3 秒，避免刚看清就被收走；

### 七、远程规则来源（0.1.6）

用户追问「如何配置规则获取地址」。先核实现状：`src/` 内 **`fetch(` 与 URL 出现次数为 0**，
规则只来自 `localStorage` 单键，且只在注册时读一次（`writeGuardConfig` 甚至没有调用点）——
即当时**不存在任何远程来源**。随后确认两条边界：来源方式为**客户端从可配置 URL 拉取**，远程权限仅限于**规则相关字段**。

新增 `src/remote.ts`（纯逻辑）与 `src/config-store.ts`（可热替换配置源）：

| 关注点 | 做法 |
| --- | --- |
| 载荷格式 | 与本机配置的规则部分同构，必须带 `"version": 1`；越界字段直接忽略 |
| 覆盖语义 | `rules` 逐条覆盖；`terms` / `termAction` / `mappings` 整体替换 |
| 本地专有 | `maskOnSubmit` / `maskOnPaste` / `remoteUrl` 远程无从改写 |
| 一致性护栏 | 合并后若不存在启用的阻断规则，拒绝远程 `rules`、保留本地规则，并在控制台说明 |
| 传输约束 | 仅 `https`；超时 1.5 秒；响应体上限 64 KiB；非 2xx / 非 JSON / 版本不符 / 超限均判失败 |
| 失败回落 | 沿用当前配置，只输出一行 `远程规则不可用，继续使用本地与缓存配置：<url>` |
| 离线可用 | 原文缓存于独立键 `...remote-cache.v1`，首屏即用缓存合成配置 |
| 热替换 | 插槽用本地 + 缓存配置**立即**注册，远程到达后经 `GuardConfigStore` + `useSyncExternalStore` 热替换 |

### 八、内置默认映射（0.1.7）

用户给出一张 67 行、去重后 41 条的 `from → to` 对照表，要求「去重后加入本地默认 mappings 配置中」。

先核实现状：`defaultGuardConfig().mappings` 为 `[]`，**包内没有任何默认映射**；而 `parseGuardConfig` 对未声明
`mappings` 的配置返回 `[]` —— 即使把清单写进默认值也不会被用上，这是「只改常量不生效」的陷阱，必须连解析语义一起改。
另用 grep 确认根 `src/**` 内没有同类映射实现，本包是唯一事实源。

| 关注点 | 做法 |
| --- | --- |
| 事实源 | 新增 `src/default-mappings.ts`，41 条去重清单（`from` 唯一、`from !== to`） |
| 注入默认 | `defaultGuardConfig().mappings` 返回清单**副本**（不共享数组，避免外部 push 污染默认值） |
| 解析语义 | 未声明 `mappings` → 默认清单；声明了 → `mergeDefaultMappings()` |
| 合并语义 | 同名 `from` 以配置为准（可改目标或用 `enabled: false` 禁用），新增条目追加在后，总数仍受 200 上限 |
| 远程一致 | `mergeRemoteConfig` 的 `mappings` 同样打底合并，避免一次远程更新把 41 条默认映射整份清空 |

关键判断：**`mappings` 由「整体替换」改为「默认打底」**。替换语义是在「映射只来自用户手写」的前提下确认的；
现在多了内置清单，若仍整体替换，任何一份显式映射（含远程下发）都会让默认清单消失，「默认映射」也就不成立。
需要清掉某条默认映射时，写同名条目并置 `enabled: false` 即可。

包含关系的安全性由既有引擎保证（`substitute` 单次扫描 + 同起点取更长命中），已用测试钉住：
`心水收纳` → `芹菜`（而非 `洋葱收纳`）、`可乐记账-鸿蒙` → `海棠`、`阿柴记账-海外` → `牡丹`。
ASCII 词条（`Feel+` 含正则元字符）经 `terms.ts` 的 `escapeRegExp` 转义后按词边界匹配，`+` 不会退化成量词。

回归覆盖：新增 `tests/default-mappings.spec.ts`（13 条：清单去重与逐条校验、默认带上清单、未声明/非数组回落、
同名改目标、同名禁用、新增追加、总数上限、远程打底、替换效果、包含关系最长优先、整段 `guard` 静默改写），
并修正 `config.spec.ts`（默认清单打底后的两处断言）与 `remote.spec.ts`（mappings 改为打底合并）。用例 145 → **158**。
